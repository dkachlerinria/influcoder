# Multi-agent coordination

Ground rules for running several Claude Code agents against this repo at the
same time without them clobbering each other's work. Read this before
starting a session if you know other agents may be active concurrently.

## 1. Never work directly in the primary checkout if another agent might be active

The primary checkout at `~/year1/rebut_ie/influcoder` is single-working-tree —
two agents editing files there at once will interleave edits and corrupt
each other's changes, even on unrelated files, because `git status`/`diff`/
`commit` only see one working tree's state.

Before starting concurrent work, each agent (other than the first) should
create its own git worktree on its own branch:

```bash
git worktree add ../influcoder-<short-task-name> -b agent/<short-task-name>
cd ../influcoder-<short-task-name>
```

Work, commit, and test entirely inside that worktree. Merge back to `main`
via a normal `git merge` or PR once done, then remove the worktree:

```bash
git worktree remove ../influcoder-<short-task-name>
```

If you were invoked with the `Agent` tool's `isolation: "worktree"` option,
this is already handled for you.

## 2. Claim a module before editing it

The codebase is deliberately split by concern (see `README.md`'s Layout
section) specifically so concurrent agents can work on different files
without conflicting:

| File | Owns |
|---|---|
| `run.py` | preset definitions, orchestration, CLI, `results.json` shape |
| `influcoder/data.py` | BBH/Dolly loading, disjoint splits, text views |
| `influcoder/gradients.py` | LoRA featurizer, CountSketch, projection-fidelity check |
| `influcoder/encoder.py` | bi-encoder distillation, training loop |
| `influcoder/metrics.py` | Spearman metrics |

Before touching a file, add a row to the **Active work** table below (in the
primary checkout, as a quick separate commit — this file is the one
exception to "don't share a working tree," since edits to it are small and
sequential). Remove your row when you merge back to `main`. If a file you
need is already claimed by someone else's in-flight task, coordinate with
the user rather than editing it out from under them.

### Active work

| Agent / branch | File(s) | Task | Started |
|---|---|---|---|
| agent/sample-eff | `influcoder/baselines.py`, `influcoder/logra.py` (cherry-picked from agent/baselines), `compare_baselines_on_sample_eff_data.py` (new) | Score LESS/LoGRA/RDS+/TF-IDF/embedding on the same fixed 100x100 eval set + GTs as the sample-eff sweep | 2026-07-13 |

## 3. Don't touch `legacy-pipeline`

The `legacy-pipeline` git tag and the `tis-ie` repo it mirrors are a
read-only correctness oracle (see README's "Correctness anchor" section and
project memory). Never rewrite, rebase, or force-push anything that moves
this tag.

## 4. `runs_out/` is scratch, not shared state

`runs_out/` is gitignored and regenerated by `run.py`. If two agents run the
same `--preset` concurrently in the *same* checkout, they'll race on the
same output directory. Each worktree gets its own `runs_out/`, so this is
only a risk if agents share a checkout — another reason to use separate
worktrees per (1).

## 5. Before merging to `main`

Run the relevant preset to confirm nothing broke:

```bash
python run.py --preset sanity
```

`sanity` also re-runs the projection-fidelity check (exact vs. sketched
gradient cosines), which is the fastest signal that a change to
`gradients.py` broke correctness.

## 6. Commit hygiene

- Small, focused commits per module — don't bundle unrelated changes across
  the ownership boundaries in (2).
- Never force-push `main`.
- If you rebase your feature branch on `main`, do it in your own worktree
  only.
